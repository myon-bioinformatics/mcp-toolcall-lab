# `jev_shim` / `jev_typesafe` — TypeSafe's real "Jev" wire shape, offline and live

## Changelog: this doc was wrong, and here's the correction

The original version of this module guessed TypeSafe's "Jev" response shape
from a secondhand blog post describing a model that answers only three
schema-constrained primitives (a yes/no probability, a weighted score +
distribution, a classification + distribution). That description was
**incomplete and, in the response field names, factually wrong**. It shipped
merged (PR #29) with an invented shape: `{"probability": ...}` for noul,
`{"score", "distribution", "confidence"}` for score, `{"choice",
"distribution", "confidence"}` for choice.

The correction below replaces that guess with TypeSafe's actual, confirmed
`POST /v1/systemone` contract, reconstructed by reading three real
open-source clients of the product plus the official `typesafe-sdk` PyPI
package's OpenAPI-generated schema. `docs.typesafe.ai` itself — including the
`llms.txt` one of those clients' own contributor guidelines points readers
to before touching this contract — is blocked by this sandbox's egress
policy (`EGRESS_BLOCKED` via both `WebFetch` and direct `curl`, "organization
policy" per this environment's proxy). The sources below were read instead;
nothing here has been checked against TypeSafe's actual docs page.

## What this is not

Neither `jev_shim.py` nor `jev_typesafe.py` has any relationship to TypeSafe
beyond modeling its publicly documented (via the sources above) wire format.
`jev_shim.py` calls no external API at all. `jev_typesafe.py` builds real
requests and can post them for real, but **no TypeSafe API key exists in
this sandbox, and no call to the real `api.typesafe.ai` has ever been made**
by this repo or its tests — see "What's actually been verified" below.

## The real contract

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <TYPESAFE_API_KEY>
Accept: application/json
Content-Type: application/json

{
  "state": <string | object | array>,
  "model": "jev-latest",
  "questions": {
    "<name>": {
      "type": "noul" | "choice" | "score",
      "instructions": <string | object | array | null>,   // optional
      "criteria": ...                                       // shape depends on type, see below
    }
  }
}
```

`criteria` per question type:

- `noul`: optional `{"true": ..., "false": ...}` guidance.
- `choice`: required `{"<label>": "<description or null>", ...}`.
- `score`: required **ordered** list of level descriptions, e.g.
  `["no coverage", "basic happy-path only", "thorough"]` (index 0 first).

A single request can carry **multiple named questions** — every real client
read above does this ("speculative fan-out": e.g. `kind`, `site`, `item` all
asked about the same screenshot state in one call), rather than one question
per round trip.

Response:

```json
{
  "model": "jev-latest",
  "answers": {
    "<name>": {"type": "noul", "noul": 0.98}
  },
  "usage": {"input_tokens": 120, "output_tokens": 12}
}
```

The three answer shapes (these are exactly what `jev_shim.validate_*_payload`
checks):

| Kind | Response shape |
| --- | --- |
| `noul` | `{"type": "noul", "noul": 0.0-1.0}` |
| `choice` | `{"type": "choice", "choice": str, "confidence": 0.0-1.0, "probabilities": {option: prob}}` |
| `score` | `{"type": "score", "score": number, "confidence": 0.0-1.0, "legend": {"0": desc, "1": desc, ...}, "probabilities": {"0": prob, "1": prob, ...}}` |

Two corrections from the original guess, both confirmed by all three client
repos and the SDK schema:

1. Answers are **native JSON fields returned directly** — not a
   chat-completion string requiring a second parse (the original design
   modeled this as OpenAI-style `choices[0].message.content`; it isn't).
2. `score`'s `legend` and `probabilities` are keyed by the **string form of
   the rubric's 0-based position** (`"0"`, `"1"`, `"2"`, ...), matching the
   ordered `criteria` list's index — not arbitrary labels like `"low"` /
   `"high"` as the original guess assumed.

## What this is

Two separate, narrower pieces:

- **`jev_shim.py`**: judges a *recorded* completion string against the real
  wire shape above, offline. Same philosophy as `prompt_experiment.py`:
  fixtures record a hypothetical completion plus ground truth, and
  `replay_case` scores it. **Nothing in `jev_shim.py` opens a socket.** A
  response is schema-valid only if it parses as JSON and matches its kind's
  shape exactly (no missing/extra top-level keys, right types, probabilities
  in range, `score` keys ordinal and matching between `legend` and
  `probabilities`). Free text, or JSON missing a required field, is
  schema-invalid — the `noul_malformed_output` fixture exists to show this
  and how it's scored (excluded from calibration, not silently treated as a
  wrong-but-valid answer).
- **`jev_typesafe.py`**: builds a real `/v1/systemone` request body
  (`build_system_one_request`, plus `noul_question` / `choice_question` /
  `score_question` helpers) and parses a real response body
  (`parse_system_one_response`), matching the contract above exactly.
  `TypeSafeClient` wraps this with an injectable `post` (defaulting to a
  real `urllib` POST with the real headers) so tests never need a live API
  key.

`jev_answerer.py` (PR #31, a separate module) is neither of these — it
prompts an arbitrary OpenAI-compatible chat backend (e.g. llama.cpp's
`/v1/chat/completions` with `response_format: json_schema`) into producing a
similar three-shape JSON object as free-form model output. That's a
"generic LLM imitating the vocabulary" experiment, not a TypeSafe client; it
predates this correction and models the *original, since-corrected* guessed
shape, not the real one documented here.

## Calibration, not just pass/fail

`calibration_summary()` computes the [Brier score](https://en.wikipedia.org/wiki/Brier_score)
over schema-valid `noul` cases: mean squared error between the declared
`noul` probability and the 0/1 ground truth. `0.0` is a perfect forecaster,
`0.25` is what an uninformative "always 0.5" forecaster scores, `1.0` is a
maximally confident, maximally wrong one. A schema-valid response can still
be badly calibrated (see `noul_overconfident_wrong.json`, a 0.97-confident
call that was wrong) — schema validity and calibration are different axes.

## What's actually been verified

- `jev_shim.py`'s validators and all 5 fixtures: verified by running
  `python -m mcp_toolcall_lab.jev_shim replay` — all 5 pass against the
  corrected shapes.
- `jev_typesafe.py`'s request building and response parsing: verified with
  injected fake `post` functions (`tests/test_jev_typesafe.py`) — proves the
  logic, not a live server.
- `jev_typesafe.py`'s actual HTTP transport (`urllib_post`, real headers,
  real JSON body over a real socket): verified against a real
  `http.server` loopback server in
  `test_urllib_post_against_real_loopback_server` — proves the stdlib
  transport code works end to end over a real socket.
- **Not verified**: that `api.typesafe.ai` itself behaves exactly as
  documented here. No API key exists in this sandbox and no request has
  been sent to the real endpoint. This module is accurately modeled on the
  sources cited above, not proven against the live API.

## Usage

```bash
python -m mcp_toolcall_lab.jev_shim replay --out test-results/jev-shim.jsonl
```

Fixtures live in `fixtures/jev_shim/*.json`. Each has an `id`, `kind`,
`state`, the kind-specific input (`proposition` / `criteria` / `options`), a
`raw_completion` (the recorded string, in the real wire shape above), a
`ground_truth`, and an `expected` block asserting a subset of the audit
fields (same convention as `prompt_experiment.py`'s fixtures).

```python
from mcp_toolcall_lab.jev_typesafe import TypeSafeClient, noul_question

client = TypeSafeClient()  # reads TYPESAFE_API_KEY from the environment
answers = client.system_one("some state", {"is_ready": noul_question()})
```

## Non-goals (explicit)

- Not a full SDK for TypeSafe's API — no retries, streaming, or model
  listing (`GET /v1/models`); just the one endpoint this study needed.
- Not full JSON Schema — `jev_shim`'s validation is hand-written and
  shape-specific, matching this repo's existing style (see
  `prompt_experiment.py`'s `raw_schema_valid`) rather than adding a
  `jsonschema` dependency.
- Not a live-API integration test — see "What's actually been verified".
